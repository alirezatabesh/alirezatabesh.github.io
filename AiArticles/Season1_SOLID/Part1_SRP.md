# فصل اول — اصل اول SOLID

# Single Responsibility Principle (SRP)

> **"یک کلاس نباید فقط یک کار انجام دهد؛ بلکه باید فقط یک دلیل برای تغییر داشته باشد."**

---

## مقدمه

اگر از اکثر برنامه‌نویسان بپرسید **SRP چیست؟**، معمولاً این پاسخ را می‌شنوید:

> «هر کلاس باید فقط یک کار انجام دهد.»

این جمله آن‌قدر تکرار شده که تقریباً به تعریف رسمی SRP تبدیل شده است؛ اما حقیقت این است که **این تعریف دقیق نیست** و در بسیاری از پروژه‌های واقعی باعث برداشت اشتباه می‌شود.

تعریف اصلی SRP که توسط **Robert C. Martin (Uncle Bob)** ارائه شده، این است:

> **A module should have one, and only one, reason to change.**

یعنی:

> **هر ماژول (یا کلاس) باید تنها یک دلیل برای تغییر داشته باشد.**

در نگاه اول ممکن است تفاوت این دو جمله ناچیز به نظر برسد، اما همین تفاوت کوچک، مرز بین طراحی متوسط و طراحی حرفه‌ای است.

---

# چرا «یک کار» تعریف مناسبی نیست؟

فرض کنید کلاس زیر را داریم:

```csharp
public class OrderRepository
{
    public void Insert(Order order) { }

    public void Update(Order order) { }

    public void Delete(int id) { }

    public Order GetById(int id) { }

    public IEnumerable<Order> Search(...) { }
}
```

اگر معیار ما این باشد که **هر کلاس فقط یک کار انجام دهد**، ممکن است نتیجه بگیریم:

- Insert یک کار است.
    
- Update یک کار دیگر است.
    
- Delete هم کار دیگری است.
    

پس باید پنج کلاس مختلف بسازیم.

اما آیا واقعاً چنین طراحی‌ای منطقی است؟

قطعاً خیر.

تمام این متدها متعلق به **یک مفهوم واحد** هستند:

> **Persistence یا دسترسی به داده**

اگر فردا تصمیم بگیریم SQL Server را با PostgreSQL جایگزین کنیم، احتمالاً همه این متدها تغییر خواهند کرد.

اما اگر قوانین کسب‌وکار تغییر کنند، این کلاس نباید تغییری کند.

بنابراین این کلاس فقط **یک دلیل برای تغییر** دارد و کاملاً با SRP سازگار است.

---

# مسئولیت (Responsibility) یعنی چه؟

کلمه‌ی Responsibility در SRP به معنای "وظیفه" نیست.

بلکه منظور از Responsibility در این اصل، همان چیزی است که باعث تغییر کلاس می‌شود.

به همین دلیل Uncle Bob بعدها تعریف دقیق‌تری ارائه کرد:

> **A responsibility is a reason to change.**

یعنی:

> **مسئولیت، همان دلیل تغییر است.**

---

# Actor؛ عمیق‌ترین نگاه به SRP

یکی از مهم‌ترین مفاهیمی که بعدها به توضیح SRP اضافه شد، مفهوم **Actor** است.

تعریف ساده‌ی Actor:

> **Actor کسی (یا گروهی) است که ممکن است از شما بخواهد کلاس را تغییر دهید.**

این Actor می‌تواند:

- تیم مالی
    
- تیم منابع انسانی
    
- تیم امنیت
    
- تیم زیرساخت
    
- Product Owner
    
- یا حتی یک قانون جدید دولتی باشد.
    

به جای اینکه از خودتان بپرسید:

> «این کلاس چند کار انجام می‌دهد؟»

بپرسید:

> **چه کسانی ممکن است درخواست تغییر این کلاس را بدهند؟**

اگر پاسخ بیش از یک گروه باشد، احتمالاً SRP نقض شده است.

---

# مثال

فرض کنید کلاسی به شکل زیر داریم:

```csharp
public class EmployeeService
{
    public void CalculateSalary() { }

    public void GenerateTaxReport() { }

    public void SendPayrollEmail() { }
}
```

چه کسانی ممکن است این کلاس را تغییر دهند؟

|Actor|دلیل تغییر|
|---|---|
|تیم مالی|تغییر نحوه محاسبه حقوق|
|دولت|تغییر قوانین مالیاتی|
|تیم Notification|تغییر نحوه ارسال ایمیل|

سه Actor مختلف.

سه دلیل برای تغییر.

در نتیجه این کلاس SRP را نقض کرده است.

---

# یک مثال واقعی

فرض کنید سیستم ثبت سفارش نوشته‌ایم.

```csharp
public class OrderService
{
    public void Create(Order order)
    {
        Validate(order);

        Save(order);

        SendEmail(order);

        Log(order);
    }
}
```

در نگاه اول شاید بگوییم:

> این کلاس فقط "ثبت سفارش" انجام می‌دهد.

اما بیایید دقیق‌تر نگاه کنیم.

چه چیزی ممکن است تغییر کند؟

اعتبارسنجی.

ذخیره در دیتابیس.

ارسال ایمیل.

ثبت لاگ.

این چهار تغییر معمولاً توسط چهار گروه مختلف ایجاد می‌شوند.

در نتیجه کلاس چهار دلیل برای تغییر دارد.

---

# بازطراحی

بهتر است هر مسئولیت را جدا کنیم.

```csharp
public class OrderValidator
{
    public void Validate(Order order)
    {
    }
}
```

```csharp
public class OrderRepository
{
    public void Save(Order order)
    {
    }
}
```

```csharp
public class EmailService
{
    public void Send(Order order)
    {
    }
}
```

```csharp
public class AuditLogger
{
    public void Log(Order order)
    {
    }
}
```

و کلاس اصلی تنها هماهنگ‌کننده باشد.

```csharp
public class OrderService
{
    private readonly OrderValidator _validator;
    private readonly OrderRepository _repository;
    private readonly EmailService _email;
    private readonly AuditLogger _logger;

    public void Create(Order order)
    {
        _validator.Validate(order);

        _repository.Save(order);

        _email.Send(order);

        _logger.Log(order);
    }
}
```

اکنون هر کلاس فقط توسط یک Actor تغییر می‌کند.

---

# آیا OrderService خودش SRP را نقض نمی‌کند؟

این سؤال یکی از بهترین سؤال‌هایی است که می‌توان درباره SRP پرسید.

در نگاه اول OrderService:

- اعتبارسنجی می‌کند.
    
- ذخیره می‌کند.
    
- ایمیل می‌فرستد.
    
- لاگ ثبت می‌کند.
    

پس ظاهراً چند کار انجام می‌دهد.

اما واقعیت چیز دیگری است.

این کلاس هیچ‌کدام از این کارها را انجام نمی‌دهد.

بلکه فقط آن‌ها را **هماهنگ (Orchestrate)** می‌کند.

تنها دلیل تغییر این کلاس، تغییر فرآیند ثبت سفارش است.

اگر الگوریتم ارسال ایمیل تغییر کند، EmailService تغییر می‌کند.

اگر دیتابیس تغییر کند، Repository تغییر می‌کند.

اگر قوانین اعتبارسنجی تغییر کند، Validator تغییر می‌کند.

OrderService فقط زمانی تغییر می‌کند که **جریان ثبت سفارش** تغییر کند.

به همین دلیل Orchestratorها معمولاً با SRP سازگار هستند.

# Responsibility با Feature فرق دارد

یکی از اشتباهات رایج این است که فکر کنیم هر Feature یک Responsibility است.

مثلاً:

```text
Invoice
```

درون این Feature ممکن است وجود داشته باشد:

- محاسبه مالیات
    
- چاپ PDF
    
- ارسال ایمیل
    
- ثبت Audit
    

همه مربوط به Invoice هستند.

اما دلیل تغییر هر کدام متفاوت است.

پس Feature نمی‌تواند معیار تشخیص SRP باشد.

---

# تعداد متدها هیچ اهمیتی ندارد

گاهی دیده می‌شود که برنامه‌نویسان می‌گویند:

> "این کلاس ۳۰ متد دارد، پس SRP را نقض کرده است."

تعداد متدها هیچ ارتباطی با SRP ندارد.

ممکن است Repository صدها متد داشته باشد.

اما تمام آن‌ها متعلق به Persistence باشند.

در نتیجه SRP رعایت شده است.

از طرف دیگر:

```csharp
public class Notification
{
    public void Save() {}

    public void SendEmail() {}
}
```

فقط دو متد دارد.

اما دو دلیل مستقل برای تغییر دارد.

پس SRP نقض شده است.

---

# رابطه SRP و Cohesion

SRP در عمل باعث افزایش **Cohesion** می‌شود.

Cohesion یعنی:

> اعضای یک کلاس باید ارتباط مفهومی بسیار نزدیکی با یکدیگر داشته باشند.

مثال مناسب:

```text
Customer
    Name
    Email
    Phone
```

تمام اعضا به مفهوم Customer مربوط هستند.

اما:

```text
Customer
    CompressImage()
    ExportExcel()
    SendSms()
```

این متدها هیچ ارتباط مفهومی با Customer ندارند.

Cohesion پایین است.

و معمولاً این نشانه‌ای از نقض SRP است.

---

# کلاس‌های Helper؛ بوی بد طراحی

یکی از رایج‌ترین اشتباهات، ساخت کلاس‌هایی مانند این‌هاست:

```text
Helper

Utils

Common

General

Manager
```

این نام‌ها معمولاً نشان می‌دهند که هنوز مسئولیت واقعی کلاس کشف نشده است.

برای مثال:

```text
ValidationHelper
```

اگر شامل اعتبارسنجی کاربر، سفارش، پرداخت، فایل و گزارش باشد، در واقع چندین Actor مختلف را در یک کلاس جمع کرده است.

این کلاس احتمالاً SRP را نقض می‌کند.

---

# بهترین سؤال هنگام طراحی

هر زمان در مورد یک کلاس شک داشتید، این سؤال را از خودتان بپرسید:

> **اگر فردا لازم باشد این کلاس تغییر کند، چه کسی درخواست این تغییر را خواهد داد؟**

اگر پاسخ شما چیزی شبیه این باشد:

- تیم مالی
    
- تیم امنیت
    
- تیم زیرساخت
    
- تیم محصول
    

همگی برای یک کلاس...

احتمالاً باید دوباره طراحی را بررسی کنید.

---

# برداشت اشتباه رایج

❌ هر کلاس فقط یک متد داشته باشد.

❌ هر کلاس فقط یک کار انجام دهد.

❌ کلاس‌های بزرگ همیشه بد هستند.

❌ اگر تعداد متدها زیاد شد SRP نقض شده است.

---

# برداشت صحیح

✅ هر کلاس باید فقط یک دلیل برای تغییر داشته باشد.

✅ هر کلاس باید متعلق به یک Actor مشخص باشد.

✅ تغییرات مرتبط باید کنار هم باشند.

✅ تغییرات نامرتبط نباید در یک کلاس جمع شوند.

---

# جمع‌بندی

Single Responsibility Principle بیش از آنکه درباره تقسیم کردن کلاس‌ها باشد، درباره **مدیریت تغییرات** است.

هدف SRP کوچک کردن کلاس‌ها نیست.

هدف آن این است که تغییرات ناشی از یک Actor در یک محل متمرکز شوند و تغییرات Actorهای مختلف روی یکدیگر اثر نگذارند.

به همین دلیل، هنگام طراحی کلاس‌ها بهتر است به جای پرسیدن:

> «این کلاس چند کار انجام می‌دهد؟»

همیشه این سؤال را مطرح کنیم:

> **«چه کسی ممکن است فردا از من بخواهد این کلاس را تغییر دهم؟»**

پاسخ این سؤال، در بسیاری از مواقع، مرز بین یک طراحی معمولی و یک طراحی حرفه‌ای را مشخص می‌کند.
